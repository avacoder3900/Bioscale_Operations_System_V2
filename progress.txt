## Codebase Patterns

### Server File Pattern
Every `+page.server.ts` follows:
1. Import: `connectDB`, models, `requirePermission`
2. Guard: `requirePermission(locals.user, 'domain:read|write')`
3. Connect: `await connectDB()`
4. Query: Mongoose `.find()`, `.findById()`, `.aggregate()` with `.lean()`
5. Serialize: `JSON.parse(JSON.stringify(result))`
6. Return: exact shape from CONTRACT-REGISTRY.md

### Auth Pattern
- `event.locals.user` — authenticated user (set by hooks.server.ts)
- `event.locals.session` — session object
- `requirePermission(locals.user, 'permission:string')` — throws error(403) if missing
- `hasPermission(user, 'perm')` — boolean check (used in layouts for UI flags)
- `isAdmin(user)` — defined but currently unused
- Cookie: `auth-session`, SHA-256 hashed, looked up in `sessions` MongoDB collection
- Auth library: custom implementation on `@oslojs/crypto` + `@oslojs/encoding` (Lucia was removed in the Postgres→MongoDB migration)

### ID Generation
```typescript
import { generateId } from '$lib/server/db/models';
const id = generateId(); // nanoid string
```

### Denormalization Pattern
At write time, embed operator/user/project info:
```typescript
createdBy: { _id: user._id, username: user.username }
project: { _id: project._id, name: project.name, color: project.color }
```

### Sacred Document Pattern
- Check `finalizedAt` before any mutation
- Use `corrections[]` array for post-finalization fixes
- Write-once phases on CartridgeRecord: check `phase.recordedAt: { $exists: false }`

### Immutable Log Pattern
- AuditLog, ElectronicSignature, InventoryTransaction, DeviceEvent, ManufacturingMaterialTransaction
- Append only — never update or delete
- Mongoose middleware blocks `.updateOne()`, `.deleteOne()`, etc.

### API Auth Pattern (Agent API)
```typescript
// Centralized: src/lib/server/api-auth.ts (timing-safe comparison)
import { requireAgentApiKey } from '$lib/server/api-auth';
// Note: 9 endpoints still use local inline requireApiKey() — consolidation needed
```

### Deployment Rule (MANDATORY)
**NEVER deploy to Vercel from local.** Always:
1. Commit to the feature branch
2. `git push origin <branch>` to GitHub
3. Deploy from GitHub via Vercel (linked to the repo)
No `npx vercel` from local working directory. All deployments must be traceable to a GitHub commit.

## Phase 11: Mongoose Subdocument ObjectId Fix (Mar 24, 2026)

### Problem
New users created through the admin UI got 500 errors on every page load. Root cause: Mongoose auto-generates ObjectId `_id` on subdocument arrays unless explicitly disabled with `{ _id: false }`. The `user.roles[]` subdocument was missing this flag. SvelteKit cannot serialize ObjectId objects.

This only affected users whose roles were assigned through Mongoose (admin UI). Users created via raw MongoDB driver (seed scripts) were unaffected because the driver doesn't add auto-generated `_id` fields.

### Fixes applied
1. **Schema fixes** — Added `_id: false` to 11 subdocument arrays across 8 model files:
   - `user.ts`: roles, communicationPreferences
   - `bom-item.ts`: versionHistory
   - `cartridge-record.ts`: tubeRecords, parts, spectroReadings
   - `manufacturing-settings.ts`: rejectionReasonCodes
   - `opentrons-robot.ts`: recentHealthSnapshots
   - `reagent-batch-record.ts`: tubeRecords, cartridgesFilled
   - `shipping-package.ts`: cartridges
   - `test-result.ts`: readings

2. **Layout serialization** — All 8 layouts that return `locals.user` now wrap with `JSON.parse(JSON.stringify())` as defense-in-depth

3. **Data cleanup** — Removed existing ObjectId `_id` from 2 affected user accounts via `scripts/fix-role-objectids.ts`

4. **Documentation** — CLAUDE.md updated with `_id: false` pitfall

### Impact assessment
- The 11 schema fixes are preventative — most load functions already manually map fields, so the ObjectId never reached the client
- The layout serialization was the actual fix for the 500 error — layouts pass the full user object unfiltered
- The larger codebase was not affected

### Unified Timeline View (primary diagnostics view)
Stitches all 4 data sources into one chronological feed per device:
- **Firmware log lines** — extracted from `device_logs.logLines[]`, each line positioned at wall-clock time
- **Webhook round-trips** — from `webhook_logs`, expandable request/response
- **Crash reports** — from `device_crashes`, expandable checkpoint sequence trail
- **Raw events** — from `device_events`, muted styling

### Key Technical Learnings

**Timestamp computation for firmware lines:**
The firmware `ms` values are millis since boot. The Lambda's `bootTime` field is unreliable — it falls back to `new Date()` (upload time) when it can't parse a boot time from the log text. Using `bootTime + ms` causes firmware lines to appear 20+ minutes in the future.

**Correct formula:** `wallClock = uploadedAt - maxMsInChunk + line.ms`. This anchors the last line of each upload chunk at `uploadedAt` and works backwards. Firmware lines then correctly interleave with webhook/event entries that use server wall-clock time.

**Upload chunks vs sessions:**
The device uploads every ~60 seconds during idle. Each upload chunk gets metadata headers prepended (`======== UPLOAD METADATA ========`, `Boot #N | Device:...`, `Firmware: vN | Format: vN`). These are NOT separate boot sessions — multiple chunks share the same `bootCount`. The BIMS groups uploads by `bootCount` and only shows a `SESSION START` boundary when `bootCount` changes (actual reboot).

**Metadata line filtering:**
Upload metadata lines (UPLOAD METADATA, `====` separators, `Boot #N |`, `Firmware: vN |`) are filtered from the timeline and session log views. The middleware already extracts `firmwareVersion` and `bootCount` as top-level document fields, so data isn't lost.

**Clock skew between sources:**
Firmware `ms` timestamps are from the device's internal clock; webhook/event timestamps are from Lambda/Particle Cloud servers. There can be 1-3 seconds of skew. This doesn't affect debugging — the relative ordering within each source is always correct. The UI shows both the wall-clock time and the firmware `ms` offset for each entry.

1. **Oven tile hardcoded `count: 0`** in cartridge-dashboard/+page.server.ts:146-151.
2. **BackingLot.cartridgeCount never decremented** — set once at WI-01 time, stayed

### MOCREO half-hour heartbeat with reminder cadence + auto-resolve (`cf621bd`)

The 5-min sync at `/api/cron/mocreo` already detected gateway outages
and fired a single email, but never re-emailed and never auto-resolved
— operators stayed in the dark while the gateway stayed down. Adds
`/api/cron/mocreo-heartbeat` at `*/30 * * * *` that re-emails every 30
min while the outage persists and clears the alert + sends a recovery
email when probes start reporting again.

Lifecycle of a `gateway_outage` alert:
- t=0      5-min sync detects outage → creates alert + initial email
- t=30/60  heartbeat sees still-open alert + lastNotifiedAt ≥ 25min ago
           → sends reminder #1, #2, ... (subject prefixes "[REMINDER #N]")
- t=Nm     readings resume → either cron auto-resolves + recovery email

Heartbeat is **DB-only** — it reads `TemperatureReading` and the open
alert from Mongo, never calls the MOCREO API. So it correctly fires on
cascade loss, building power loss, gateway crash, AND if the 5-min sync
itself stops firing for any reason. Reminder threshold is 25min, not 30,
to give the cron 5min of slack so a slightly-late fire doesn't skip a
beat (Vercel cron timing isn't second-precise).

Two guard rails on the email side:
- Defensive create only fires on confirmed outage signal
  (`haveSignal && isOutage`) — no false alarms when there's no probe data
- Auto-resolve requires positive evidence (`haveSignal && !isOutage`).
  An outage that outlasts the 7-day reading lookback returns
  `reminder_sent` (alert stays open, reminders continue) rather than
  falsely emailing "Gateway recovered."

Schema additions on `TemperatureAlert`: `lastNotifiedAt`,
`notificationCount`, `resolvedAt`, `resolvedReason` (all backward-compat).
`notifyGatewayOutage` accepts optional `firstSeenAt` + `reminderNumber`
so reminders render with downtime + reminder count in the subject. New
`notifyGatewayRecovered` for the recovery one-shot. The 5-min sync also
auto-resolves on recovery so both crons converge on the same state
whichever fires first. Verified via `scripts/sim-mocreo-heartbeat.ts`
(10 cases).

### Follow-up — Stale layout data on within-kanban navigation (same session)

Jacob hit a different bug: fold state didn't persist when navigating
between sibling kanban routes (/kanban → /kanban/list → /kanban). Worked
fine on hard refresh or cross-layout navigation.

Root cause: SvelteKit caches `+layout.server.ts` data and doesn't re-run
the load function on sibling-route navigations. So `data.projects`
stayed stale (pre-click `collapsed` values) even after the DB POST
succeeded. On return to /kanban, the page component re-mounted and
the `$state(...)` Set initializer read the stale cached layout data.

Fix:
- `kanban/+layout.server.ts` — `depends('kanban:projects')` tags the
  layout for explicit invalidation.
- `kanban/+page.svelte` — `invalidate('kanban:projects')` after each
  successful UI-state POST. Layout re-runs in the background, so the
  next time the page remounts (sibling-route navigation), its $state
  initializer reads fresh `data.projects`.

Note: $state initializers only run once at mount — they don't re-run
when `data` changes during the component's lifetime. That's intentional
here: the optimistic local state IS the source of truth while the page
is open. The invalidation ensures the SERVER data catches up so future
remounts start from the correct baseline.

### The capture 500 — root cause + fix

Two stacked bugs, surfaced one after the other by testing on prod:

1. Legacy data: 475 of ~756 `cartridge_records` have `photos` stored as
   `{}` (object) instead of `[]`. The endpoint's `$push: { photos }`
   throws "must be an array but is of type … in document {_id:<cart>}"
   → 500 on every capture to a bad cart. (This was the long-known,
   previously-deferred photos[] defect — see memory.)
   Fix: replaced `$push` with a pipeline update that coerces photos to
   `[]` when it isn't an array, then appends — self-heals each cart on
   first capture:
     [{ $set: { photos: { $concatArrays: [
        { $cond: [{ $isArray: '$photos' }, '$photos', []] },
        { $literal: [photoEntry] } ] } } }]

2. Mongoose 9 gotcha: array (aggregation-pipeline) updates THROW at
   runtime — "Cannot pass an array to query updates unless the
   `updatePipeline` option is set" — unless you pass
   `{ updatePipeline: true }` as the options arg. This is NOT caught by
   `npm run check` (the types accept the array), so it passed local
   type-check and only failed live. Fixed by adding the option.

### Knowledge learned (reusable — read before similar work)

- VERCEL PREVIEW ENV: Preview deployments only get env vars scoped to
  the Preview environment. Production-only secrets (R2_WORKER_URL,
  R2_UPLOAD_SECRET, R2_PUBLIC_URL, R2_BUCKET_NAME — see
  src/lib/server/services/r2.ts) are ABSENT on branch/preview deploys, so
  `/api/cv/capture` 500s with "R2_WORKER_URL not configured" on a preview
  even though scan/lookup (Mongo reads) work fine. To test capture either
  run on a deploy that has the R2 vars, or add them to the Preview scope.
- PRODUCTION BRANCH = `main`. Repo has THREE plausible prod branches
  (main, master, dev). Confirmed this session: Vercel production deploys
  from `main` (merge → prod URL updated → capture worked). `dev` is the
  active integration branch and was ~400 commits AHEAD of main/master;
  main/master had been stale since Apr/May. master and main have also
  diverged from each other historically.
- MONGOOSE 9 pipeline updates need `{ updatePipeline: true }` (runtime,
  not type-checked). See above.
- LOCAL BUILD ON WINDOWS can't finish `@sveltejs/adapter-vercel`: OOM at
  Node's 4GB default, and even at 8GB it dies on
  `EBUSY readlink 'C:\swapfile.sys'` (the Vercel file-tracer choking on
  the Windows swap file). Both are LOCAL-only; Vercel's Linux builders
  are fine. The meaningful local signal is the Vite build itself
  (`✓ built in …`) — that's what catches real code errors; the adapter
  packaging step can be ignored locally.
- PI STATION VIDEO is a DIRECT browser↔Pi WebRTC connection
  (`wss://<station>/ws`). BIMS is NOT in the media path — it only mints a
  5-min HS256 JWT signed with `station.jwtSecret` from Mongo
  (deployment-independent). So switching BIMS deployments cannot break
  video. "No video" this session was a stale connection from an old tab;
  reconnect/refresh fixed it. The Pi agent supports `trigger_scan` and
  tags scans `triggered` (agent.py); station capture is a browser-side
  canvas snapshot of the WebRTC frame POSTed to /api/cv/capture.

## Session 2026-06-12 — CV verdict-path audit + calibration/gating PRD

### What happened

Full read-only audit of the CV pass/fail (approval) path: capture →
`runPhaseInference()` → cv-worker `/infer` → `CvInspection`. No code
changed this session. Findings logged here; the fix is spec'd in
docs/prds/CV-VERDICT-CALIBRATION-AND-GATING.md (Draft, awaiting review).

### How the verdict works today (verified, file:line)

- Capture (`/api/cv/capture`, `/api/cv/capture-ingest`) fires
  `runPhaseInference()` fire-and-forget (run-inference.ts:104-114);
  fan-out to every CvProject with `deployAtPhases ∋ phase` +
  `activeModelVersion`; CvInspection pre-inserted as `running`, then
  updated verbatim from the worker response (run-inference.ts:52-65).
- The ENTIRE approval criterion is main.py:308-318: single PaDiM
  anomaly score; sigmoid-squashed ONLY if outside [0,1]; `fail` if
  score >= threshold (trainedModels[].confidenceThreshold, default
  0.5). Shadow model runs the same way with isShadow:true.

### Root causes of bad verdicts

1. THRESHOLD IS UNCALIBRATED — PaDiM scores are unbounded distances,
   not probabilities; conditional sigmoid distorts them inconsistently
   (raw 3.0→0.95, raw 0.7→unchanged); nobody ever computed the
   threshold from labeled data. This is THE bug behind verdicts not
   tracking reality.
2. VERDICTS HAVE NO CONSEQUENCES — result is display-only (DHR +
   project pages); nothing gates cartridge flow; a CV `fail` can ship.
   No human disposition/override exists (CvImage.qcLabel is training
   labels, unrelated to inspections).
3. FRAGILE LOOP — cv-bridge.ts has NO timeout/retry (hung worker =
   inspection stuck `running` forever); worker response stored with
   zero validation (`any`); worker has NO AUTH on any endpoint
   (cv-bridge sends no header; cv-api.ts X-API-Key module is unused by
   the infer path); `defects` is a hardcoded placeholder; unbounded
   ONNX session cache (OOM risk); /tmp training data never cleaned;
   model cache filename `replace('/','_')` can collide; shadow
   inspections never filtered out of queries; promotion doesn't check
   trainedModels[].status — a 'failed' model can be set active.

### Corrections to first-pass audit (subagent claims I disproved)

- cv_inspections DOES index imageId/cartridgeRecordId/projectId
  (schema `index: true`) — "missing index" finding was WRONG.
- There is no optional X-API-Key on the infer path — cv-bridge.ts
  sends nothing. Worker is fully unauthenticated.

### The plan (see PRD for detail)

A) Calibrate at training time (score all labeled images, min-max
   normalize, F1-optimal threshold → new trainedModels fields, metrics
   via existing train-complete callback) + harden loop (timeout/retry,
   zod validation, X-CV-Secret worker auth, cache hygiene, stale-
   running sweep). B) Disposition endpoint + getCvGateStatus() soft
   gate meshing CV phases onto existing manual QC sections
   (wax_filled↔waxQc, reagent↔reagentInspection, qaqc_released↔
   qaqcRelease). C) Per-project hard gate via CvProject.enforcementMode.
   Two small .svelte surfaces flagged for freeze escalation.
